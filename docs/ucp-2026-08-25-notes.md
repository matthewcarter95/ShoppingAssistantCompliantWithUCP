# UCP 2026-08-25: confirmed shapes for the shopping agent

Sources: spec repo `Universal-Commerce-Protocol/ucp` at tag `v2026-08-25` (schemas under `source/schemas`, REST OpenAPI at `source/services/shopping/rest.openapi.json`, docs under `docs/specification`), plus live probes of the merchant `https://n5je6mqzsskozc32cqdfetl42q0augte.lambda-url.us-east-1.on.aws` on 2026-10-14.
Tags: **SPEC** = from schema/OpenAPI, **LIVE** = observed on the merchant, **GAP** = merchant differs from spec or is broken.

## 1. Discovery (`GET /.well-known/ucp`)
- LIVE: `{"ucp": {version, services, capabilities, payment_handlers}, "keys": [JWK]}`. `Cache-Control: public, max-age=3600`.
- `services` is `{ "dev.ucp.shopping": [ {version, spec, transport:"rest", endpoint, schema} ] }`. The old `rest.endpoint` shape is gone; read `endpoint` from the array entry whose `transport == "rest"`.
- `capabilities` and `payment_handlers` are **objects keyed by reverse-DNS name, each holding an array** (old shape was a list). Capabilities advertised: checkout, cart, order, discount (extends checkout+cart), fulfillment, buyer_consent, `catalog.search`, `catalog.lookup`. `extends` is a string or an array.
- `keys[]` is the top-level JWKS (EC P-256, ES256). `signing_keys[]` no longer exists.
- Payment handlers LIVE: `dev.shopify.shop_pay` (id `shop_pay`), `com.google.pay` (id `google_pay`), `dev.mock.payment_handler` (id `mock_payment_handler`, config `{}`). The handler `id` is what an instrument's `handler_id` must reference.
- GAP: no `dev.ucp.common.identity_linking` capability is advertised, and `/.well-known/oauth-protected-resource` returns 404.

## 2. Request headers (SPEC, `rest.openapi.json`)
| Header | Rule |
|---|---|
| `UCP-Agent` | **Required.** RFC 8941 dictionary, `profile="https://<agent>/.well-known/ucp"`. The URL **must be the agent's `/.well-known/ucp`**, not `/agent-profile`. No `version=` member. |
| `Request-Id` | **Required** on every call (uuid). |
| `Idempotency-Key` | **Required** on POST/PUT (uuid). LIVE: a missing key returns 422 `INVALID_REQUEST`. Not sent on GET. |
| `Authorization`, `X-API-Key` | Optional. Bearer = OAuth token (client_credentials or authorization_code). |
| `Signature`, `Signature-Input`, `Content-Digest` | Optional in OpenAPI. RFC 9421, `sha-256` digest, sig label `sig1`. Required components: `@method @authority @path`, plus `ucp-agent`, `idempotency-key` (POST/PUT), `content-digest` and `content-type` (when a body exists), `@query` if present. ES256 mandatory. |
- **`Request-Signature` does not exist in the 08-25 spec.** The current fake `request-signature: chatbot-request` header should be dropped.
- LIVE: the merchant accepts unsigned requests, even with no `UCP-Agent`. Signing is therefore a correctness/security feature of the spec, not something the merchant currently enforces.

## 3. Endpoints (SPEC = LIVE)
`POST /checkout-sessions` (201), `GET|PUT /checkout-sessions/{id}`, `POST /checkout-sessions/{id}/complete`, `POST /checkout-sessions/{id}/cancel`, `POST /carts`, `GET|PUT /carts/{id}`, `POST /carts/{id}/cancel`, `POST /catalog/search`, `POST /catalog/lookup`, `POST /catalog/product`, `GET /orders/{id}`.
The old `GET /api/ucp/products` returns 404.

## 4. Catalog
- Search request `{query, context?, signals?, filters?, pagination?}`. LIVE response: `{ucp, products:[...], pagination:{has_next_page,total_count}}`.
- Lookup request `{ids:[...]}`. `catalog/product` request `{id}`.
- Product: `{id, title, description:{plain}, url, categories, price_range:{min,max:{amount,currency}}, variants:[{id, sku, title, price:{amount,currency}, availability:{available}}], media:[{type,url,alt_text}]}`.
- **Prices are `{amount, currency}` in minor units** (2500 = $25.00). `description` is an object, not a string. The **variant `id` is the `item.id` used in checkout/cart**.
- `availability` is `{available: bool}`, not the old string `"out_of_stock"`.

## 5. Cart and checkout
- Create body: `{line_items:[{item:{id}, quantity}], ...}`. Optional `buyer {first_name,last_name,email,phone_number}`, `context`, `signals`, `attribution`, `payment`, `cart_id`.
- Response (checkout): required `ucp, id, line_items, status, currency, totals, links`. Optional `buyer, context, signals, messages, actions, policies, expires_at, continue_url, payment, order`. LIVE also returns `discounts` and `cart_id`.
- `line_items[]`: `{id, item:{id,title,price(minor units int),quantity_unit?,image_url?}, quantity(int), totals:[{type,amount}]}`. The **line item `id` is server-generated** and needed for fulfillment references.
- `totals[]`: `[{type, display_text?, amount(signed minor units)}]`; types include `subtotal, items_discount, discount, fulfillment, tax, fee, total`. **Use `type == "total"`; do not recompute.**
- `status`: `incomplete | requires_escalation | ready_for_complete | complete_in_progress | completed | canceled`. LIVE: a new session with a valid item is already `ready_for_complete`. `continue_url` (HTTPS) is mandatory for `requires_escalation`.
- Update (`PUT`) is a **full replacement**; resend `line_items` (with ids) and anything else to keep. LIVE PUT with `discounts:{codes:[...]}` works and returns `discounts.applied[]` (`code,title,amount,provisional,allocations`) and a negative `discount` total.
- Cart: `POST /carts` returns `{id:"cart_...", line_items, currency, totals, continue_url, expires_at}`. `PUT /carts/{id}` replaces line items (LIVE totals recomputed). A checkout can be created with `cart_id`; LIVE it adopts the cart's lines.
- Cancel: `POST .../cancel` returns the session with `status: canceled`.
- **Messages**: `type` = `error | warning | info`. Error requires `code, content, severity` (`recoverable | requires_buyer_input | requires_buyer_review | unrecoverable`), optional JSONPath `path`. Warning has `presentation` (`notice` default; `disclosure` must be shown). LIVE business errors use real HTTP codes here (400 / 402 / 422 / 404) with a `{ucp:{status:"error"}, messages:[...]}` body.

## 6. Fulfillment
- Method: `{id, type("shipping"|"pickup"|open string), line_item_ids[], destinations[], selected_destination_id, groups[]}`. `id` and `line_item_ids` are **required**.
- Destination: `{id, type, ...postal_address fields}`; postal address is **flat** (`street_address, address_locality, address_region, postal_code, address_country`, optional `first_name, last_name, phone_number`), **not** nested under `postal_address`. `type` and `id` required.
- Group: `{id, line_item_ids, options[], selected_option_id}`. Option: `{id, title, description{...}, carrier, earliest/latest_fulfillment_time, totals}`.
- LIVE (GAP): a `PUT` with a spec-valid `fulfillment` block returns **HTTP 500 `text/plain`**, so the fulfillment path cannot be verified end to end. Complete without fulfillment returns 400 `Fulfillment address and option must be selected before completion.` This is the known merchant fulfillment bug; fulfillment tests stay stubbed.

## 7. Complete / payment
- Spec body: `{payment:{instruments:[{id, handler_id, type, credential:{type:"token", token}, billing_address?}]}}`. The old `payment_data` + `risk_signals` wrapper is gone from the spec.
- GAP: the live merchant still **requires a top-level `risk_signals`** (422 `Field required at risk_signals` if absent). Send `risk_signals: {ip_address, user_agent}` until the merchant is fixed, then remove it.
- LIVE: `fail_token` returns 402 `INSUFFICIENT_FUNDS` with severity `requires_buyer_input`. `success_token` behavior could not be reached because of the fulfillment 500.
- Success response is the checkout with `status: completed` and `order: {id, label?, permalink_url}` (`order_confirmation`, `id` and `permalink_url` required). `complete_in_progress` has no `order`; GET with backoff, never PUT.
- Handler choice must come from discovery (`payment_handlers`), matching the handler `id` to `handler_id`.

## 8. Order (`GET /orders/{id}`)
Required: `ucp, id, checkout_id, permalink_url, line_items, fulfillment, currency, totals`. Line items carry `quantity {original,total,fulfilled}`. LIVE: unknown id gives 404 `RESOURCE_NOT_FOUND` in the standard error envelope. Scopes (from identity linking): `dev.ucp.shopping.order:read`.

## 9. Identity linking
- SPEC: scopes are declared by the business as `{capability}:{scope}` (e.g. `dev.ucp.shopping.order:read`); platform runs OAuth 2.0 authorization code + PKCE S256; handle `WWW-Authenticate: Bearer` challenges with `resource_metadata` (RFC 9728); validate `iss` (RFC 9207); resolve the authorization server via RFC 9728, then RFC 8414, OIDC only on 404.
- GAP: the merchant advertises no identity-linking capability, no protected-resource metadata, and enforces no auth on any endpoint I called. The chatbot's merchant OAuth login (new Auth0 tenant) is therefore not currently required by the merchant. Auth0 tenant metadata: `/.well-known/oauth-authorization-server` returns 200 and `authorization_response_iss_parameter_supported: true`.
- Implication: RFC 9728 discovery cannot be driven from the merchant today. Implement it so it activates when the merchant publishes metadata, and keep the configured tenant as the fallback.
